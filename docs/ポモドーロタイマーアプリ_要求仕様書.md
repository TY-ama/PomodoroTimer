今の回答をそのまま要求に落とすと、**「集中／休憩」固定ではなく、“複数の時間区間を順番に実行する汎用タイマー”**として設計するのが一番きれいだと思う。

たとえば、

`15分 → 5分 → 15分 → 5分`

という時間列を1セットとして、それを5回繰り返す、という考え方。これなら普通のポモドーロにも、別の時間配分にも対応できる。

# ポモドーロタイマーWebアプリ 要求仕様書

## 1. 目的

本システムは、指定した複数の時間区間を順番に実行し、それらを指定回数繰り返すことができるタイマーWebアプリである。

一般的なポモドーロタイマーのような「集中時間」「休憩時間」という固定的な区分に限定せず、利用者が任意の時間列を設定できるものとする。

また、前回使用した設定やプリセットをブラウザ内に保存し、次回利用時に同じ設定を容易に再利用できることを目的とする。

---

## 2. 利用対象

本システムは、PCブラウザ上で個人利用することを想定する。

スマートフォンでの利用は、本システムの対象外とする。

---

## 3. システム概要

利用者は、実行する時間区間を複数設定する。

例：

* 15分
* 5分

上記の時間列を1セットとして設定し、さらに繰り返し回数を指定することで、

`15分 → 5分 → 15分 → 5分 → …`

のように、自動的にタイマーを実行する。

各時間区間の終了時には通知音を再生し、自動的に次の時間区間へ移行する。

設定内容はブラウザ内に保存し、次回アクセス時にも再利用できるものとする。

---

# 4. 機能要求

## 4.1 タイマー設定機能

利用者は、タイマーとして実行する時間区間を設定できるものとする。

各時間区間について、以下の方法で時間を指定できること。

* 任意の時間を直接入力する
* あらかじめ用意された時間選択ボタンから選択する

時間選択ボタンとして、少なくとも以下を用意する。

* 5分
* 10分
* 15分
* 20分

なお、選択可能な時間については、今後追加・変更できる構造とする。

---

## 4.2 時間区間追加機能

利用者は、実行する時間区間を複数登録できるものとする。

例：

| 順番 | 設定時間 |
| -- | ---: |
| 1  |  15分 |
| 2  |   5分 |
| 3  |  25分 |
| 4  |  10分 |

登録された時間区間は、上から順番に実行する。

時間区間の数は固定せず、将来的に任意の個数を登録できる構造とする。

---

## 4.3 繰り返し回数設定機能

利用者は、登録した時間区間の並びを何回繰り返すか設定できるものとする。

例えば、

* 時間区間：15分 → 5分
* 繰り返し回数：5回

と設定した場合、

`15分 → 5分`

を1セットとして5回実行する。

---

## 4.4 タイマー開始機能

利用者が開始ボタンを押下すると、設定された最初の時間区間からタイマーを開始する。

タイマー開始後は、設定内容を変更できないものとする。

---

## 4.5 自動移行機能

現在の時間区間が終了した場合、自動的に次の時間区間のタイマーを開始する。

利用者による開始操作は必要としない。

現在のセット内の最後の時間区間が終了した場合、次のセットの最初の時間区間を自動的に開始する。

設定されたすべてのセットが終了した場合、タイマーを終了状態とする。

---

## 4.6 一時停止機能

利用者は、実行中のタイマーを一時停止できるものとする。

一時停止中は、残り時間を減少させない。

一時停止後、再度開始操作を行うことで、停止時点の残り時間からタイマーを再開できるものとする。

---

## 4.7 リセット機能

利用者は、現在実行中の時間区間のみをリセットできるものとする。

例えば、15分の時間区間を実行中に残り時間が8分となっている場合、リセットを行うことで残り時間を15分に戻す。

リセットを行っても、

* 現在のセット番号
* 他の時間区間
* 繰り返し回数

は変更しないものとする。

---

# 5. 通知機能

## 5.1 通知音

各時間区間が終了した際に通知音を再生する。

通知音は、タイマー画面が表示されているかどうかにかかわらず、可能な限り利用者が認識できるものとする。

---

## 5.2 音量調整

利用者は、通知音の音量を変更できるものとする。

音量設定はブラウザ内に保存し、次回利用時にも前回設定した音量を使用する。

---

## 5.3 ブラウザ通知

利用者が別のブラウザタブを表示している場合でも時間区間の終了を認識できるよう、ブラウザの通知機能を利用できるものとする。

ブラウザ通知を使用するために権限が必要な場合は、利用者に通知許可を要求する。

ブラウザ通知が許可されていない場合でも、通知音による通知は行う。

---

# 6. 表示機能

## 6.1 残り時間表示

現在実行中の時間区間の残り時間を画面上に大きく表示する。

表示形式は原則として、

`分:秒`

とする。

例：

`14:32`

---

## 6.2 セット数表示

現在実行しているセット番号と、設定された総セット数を表示する。

例：

`3 / 5 SET`

---

## 6.3 全体残り時間表示

現在時点から、すべてのセットが終了するまでのおおよその残り時間を表示する。

全体残り時間には、以下を含める。

* 現在の時間区間の残り時間
* 現在のセット内の未実行時間
* 残りセットの時間

一時停止している時間は含めない。

---

## 6.4 現在区間表示

現在、時間列のどの区間を実行しているか識別できるよう表示する。

例：

`STEP 1 / 2`

または

`15 min`

などとする。

---

# 7. 設定保存機能

## 7.1 前回設定保存

利用者が設定した以下の情報をブラウザ内に保存する。

* 時間区間の並び
* 各時間区間の設定時間
* 繰り返し回数
* 通知音量

次回Webアプリへアクセスした際には、前回利用した設定を自動的に読み込むものとする。

---

## 7.2 保存方式

設定情報は、Webブラウザの `localStorage` を利用して保存する。

そのため、データベースやサーバ側での設定保存は必須としない。

設定情報は、基本的に同一PC・同一ブラウザ内でのみ共有されるものとする。

---

# 8. プリセット機能

## 8.1 プリセット保存

利用者は、設定した時間区間と繰り返し回数を1つのプリセットとして保存できるものとする。

プリセット例：

**通常**

* 25分
* 5分
* 4セット

**短時間**

* 15分
* 5分
* 5セット

---

## 8.2 プリセット構成

1つのプリセットは、少なくとも以下の情報を保持する。

* プリセット名
* 時間区間の一覧
* 繰り返し回数

---

## 8.3 プリセット読込

保存済みプリセットを選択することで、その設定内容を現在のタイマー設定へ反映できるものとする。

---

## 8.4 初期実装範囲

初期バージョンでは、1つの設定のみを保存する構成としてもよい。

ただし、将来的に複数のプリセットを登録できるよう、データ構造には拡張性を持たせる。

---

# 9. 履歴機能

本システムでは、過去のタイマー実行履歴は保存しない。

以下の情報についても保存対象外とする。

* 過去の実行回数
* 過去の集中時間
* 日別利用時間
* タイマー完了履歴

保存対象は、原則としてタイマー設定情報のみとする。

---

# 10. 画面要求

## 10.1 デザイン

画面はダークテーマを基本とする。

視認性を重視し、不要な装飾を避けたシンプルなデザインとする。

特に現在の残り時間を画面内で最も目立つ情報として表示する。

---

## 10.2 想定画面構成

タイマー実行画面では、主に以下を表示する。

* 現在の残り時間
* 現在の時間区間
* 現在セット数 / 総セット数
* 全体残り時間
* 開始ボタン
* 一時停止ボタン
* リセットボタン

設定画面では、主に以下を操作できるものとする。

* 時間区間追加
* 時間設定
* 時間区間削除
* 繰り返し回数設定
* プリセット選択
* プリセット保存
* 音量調整

---

# 11. タイマー精度要求

Webブラウザのタイマー処理による時間ずれを抑えるため、単純に1秒ずつ残り時間を減算する方式だけに依存しない。

タイマー開始時に終了予定時刻を保持し、

`終了予定時刻 - 現在時刻`

から残り時間を算出する方式を基本とする。

これにより、別タブへの移動などによってJavaScriptのタイマー処理間隔が遅延した場合でも、大きな時間ずれが発生しないようにする。

---

# 12. システム構成要求

本システムは、原則として以下の技術で構成する。

* HTML
* CSS
* JavaScript
* Web Storage API（localStorage）
* Web Notifications API
* Web AudioまたはAudio API

タイマー処理および設定保存処理は、ブラウザ上で実行する。

---

# 13. サーバ要求

本システムでは、サーバ側での処理やデータベース保存を必須としない。

Webアプリ本体については、毎回ローカルWebサーバを起動する必要がないよう、インターネット上の静的Webホスティングサービスへ配置できるものとする。

候補として以下を想定する。

* GitHub Pages
* Cloudflare Pages
* Netlify
* Vercel

サーバは主としてHTML、CSS、JavaScriptなどの静的ファイルを配信する用途で使用する。

タイマー処理や設定保存処理そのものは、利用者のWebブラウザ上で実行する。

---

# 14. 対象外

初期バージョンでは、以下の機能を対象外とする。

* ユーザー登録
* ログイン
* 複数端末間での設定同期
* サーバデータベースへの保存
* 過去の利用履歴管理
* スマートフォン専用画面
* 他ユーザーとの設定共有

---

# 15. 今後の拡張候補

将来的には以下の機能を追加できる構造とする。

* 複数プリセットの登録
* プリセット編集
* プリセット削除
* 各時間区間への名称設定
* 通知音の選択
* タイマー実行履歴
* 利用時間の集計
* 複数端末での設定同期
* クラウドへの設定保存

特に今回の仕様で大事なのは、**内部的に「集中時間」「休憩時間」を持たせない**こと。

たとえばデータも、

```javascript
{
  intervals: [15, 5],
  repeatCount: 5
}
```

みたいに持たせる。

そうすれば将来的に、

```javascript
{
  intervals: [25, 5, 25, 10],
  repeatCount: 3
}
```

みたいな変則的なタイマーにもそのまま対応できる。

さらにプリセットまで考えるなら、最終的には、

```javascript
{
  name: "いつもの勉強",
  intervals: [
    { minutes: 15 },
    { minutes: 5 }
  ],
  repeatCount: 5
}
```

くらいの構造にしておくと拡張しやすい。次はこの要求仕様から、**画面構成 → データ設計 → JavaScriptの処理設計**まで落としていくと実装に入りやすい。
